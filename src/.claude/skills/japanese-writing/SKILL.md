# Japanese Writing

> 誇張、気取り、あいまいさ、非難を見分けるには日本語の語感が要るので、本文は日本語で書く。

開発者向けの日本語の文書（方針や計画、設計提案、会議資料、issue/PR、チーム向けの投稿）を、事実どおりで、誰が何をどうするかが一読でわかる文に直す。どこを直すかは各節の原則で決める。表の例は型を示すための見本で、すべてを挙げたものではない。

## Process

1. 対象を決める。引数か依頼文でファイルパスが渡されていればそのファイルを、なければチャットに貼られたテキストを対象にする。
2. 各節の原則を上から順に当てはめ、直す箇所を洗い出す。
3. 元の意味と構成（見出しの階層、コードブロック、図表）を保ったまま書き換える。見出しの文言はHeadingsの原則に沿って直す。原文にない事実を補わないと直せないときや、原文からは決められない解釈を選ぶ必要があるときは、書き換えず指摘として報告する。この扱いは各節の原則より優先する。
4. ファイルなら直接書き換え、変更した箇所を報告する。チャットのテキストなら、直した文をそのまま出す。すでに投稿されたテキストは貼り直せる形で出すだけにし、投稿先は書き換えない。
5. 投稿や確定の前に2〜4をもう一度行い、書き直すたびに繰り返す。一語だけの小さな直しほど前後を読み直さずに済ませやすく、誇張や造語がまた入り込む。

## Don't Overstate

事実より強く書かない。決まっていないことを決まったように書かず、確かなことを無用にぼかさない。していない計測や確認を、したかのように書かない。因果関係を書くときは、なぜそうなるかを一言添える。

| 直す対象                                                  | 直し方                                                 |
| --------------------------------------------------------- | ------------------------------------------------------ |
| 最上級や比較、大げさな言い方                              | 確かめられる事実の範囲まで弱める                       |
| 決まっていない時期や数値の決めつけ                        | 決まっている分だけ書く                                 |
| 範囲や期限の境目があいまいな書き方                        | 始まりと終わりを示し、含めるものを挙げる               |
| 根拠のない断定                                            | 推測は推測として書く。本文に根拠があるときだけ言い切る |
| 検出・保証・解決を「必ずできる」と書く                    | 条件を添える（「〜しやすい」「〜のときに限る」）       |
| 違うものをひとまとめにする、複数ある原因を1つに決めつける | 分けて書く                                             |

## Use the Reader's Words

読者がそのまま理解できる言葉を使う。次の順で決める。(1) 変数名やプロパティ名などコード上の名前は訳さない。(2) 読者に通じる定訳や定着した言葉があれば、それを使う。(3) なければ、初めて見ても意味が通るふつうの言葉に言い換える。(4) 言い換えられなければ英語のまま書き、初出で意味を一言添える。短い文書で、添える説明が本文に比べて長くなるときは、意味が多少狭まっても言い換えを選ぶ。

技術用語は**言い回し全体をひとまとまりとして**判断する。定型句や複合語（source of truth、baseline）を部品に分けて1つずつ訳すと、存在しない言葉ができる（真実源、基線）。1つずつの訳は正しいので、もっともらしく見えてしまう。

カタカナ語を残すか英語にするかは、一覧で機械的に決めない。どれだけ定着しているかと、同じ文書やコード、API、分野での表記に揃うかで決める。決めた表記は文書の中で統一する（見出しがSource of Truthなら本文でもSource of Truthと書き、Truthだけを抜き出さない）。

| 型                                                                                     | NG → OK                                                        |
| -------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 内輪でしか通じない略し方                                                               | M6目標 → 6か月時点の目標                                       |
| 英語の用語を漢字に直訳する（「回帰」「継承」など定着した訳語は除く）                   | 契約 → Promise、基線 → ベースライン、真実源 → 〜を正とする     |
| カタカナと直訳を組み合わせた言葉（直訳の部分がふつうの日本語に見えるので見逃しやすい） | メジャー更新 → Major update                                    |
| 英語をそのままカタカナにする（「コンポーネント」「トークン」など定着した語は除く）     | アナトミー → Anatomy、トランジション → transition              |
| 定訳のない外来語や略語                                                                 | クロスリポ → リポジトリをまたぐ、dead → 実際には使われていない |
| くだけた略語（通じるとしても技術文書では正式な形にする）                               | スクショ → スクリーンショット                                  |
| 漢字を並べた造語（「最適化」「正規化」など定着した言葉は除く）                         | 完成文字列 → そのまま表示できる文字列、活性化 → 有効化         |
| 気取った言い方                                                                         | 踏み込んで → 取り組む、Go/No-go判断 → 判定                     |
| 比喩をそのまま使う（英語から直訳した比喩も、自分で持ち込んだ比喩も）                   | 床 → 3:1以上、穴 → 対応していない箇所                          |
| 間の言葉を省いて縮めたせいで、主語や目的語が入れ替わる                                 | 本文全体を消費する → 本文全体がコンテキストに入る              |

## Tight and Concrete

一文ずつ、次の2点を確かめる。削っても読者に伝わる内容が減らない文は削る。誰が何をどうするかを読み取れない文には、それを書き足す。比喩や、違いや根拠を省いて結論だけを示す表現は、ふつうの言葉でも読めば意味が通るので、読み取れていないことに気づきにくい。

| 直す対象                                                         | 直し方                                                                               |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 同じ主張の繰り返し（言い換え、直後のまとめ直し）                 | 一か所にまとめる                                                                     |
| 後で使わない固有名詞、なくても困らない細部（時刻、細かい数値）   | 削る                                                                                 |
| 書く過程の名残（依頼文、制約、見送った案、直した経緯）           | 制約は書かずに、構成や手順で守る。省いたことも書かない                               |
| 抽象的な言い方や施策                                             | 言い換えや具体例を丸括弧で添え、何を指すかをその場で示す。読者に前を読み返させない   |
| 受身や名詞化（対応の検討を行う）のせいで、誰がするのかが消えた文 | するのは誰かを主語にし、動作は動詞で書く。対象を先に示すためにあえて使った受身は残す |

## No Filler

Tight and Concreteで文に当てた基準を、文の中の言い回しにも当てる。内容を足さずに文を印象的に見せるだけの言い回しは、歯切れよく言い切っていても削る。

| 直す対象                                                                                                   | 直し方                                                                 |
| ---------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 主張の前後に付ける予告、否定、留保（前に「重要なのは〜」「〜と思われがちだが」、後に「〜ではありません」） | 主張から書き始め、主張で終える。範囲や条件が要るなら主張の文の中で書く |
| 決め台詞だけの短い段落、「AではなくB」という対句の多用                                                     | ふつうの文に戻す                                                       |
| 中身のない動詞（深掘りする、言語化する、向き合う）                                                         | 何をどうするかを書くか、削る                                           |
| 中身のない形容詞（鍵となる、根本的な）                                                                     | 中身を書くか、削る                                                     |
| 強調の言葉（非常に、極めて）                                                                               | 削る。程度を示すなら具体的な数値を書く                                 |
| 「さらに」「また」「加えて」の連続                                                                         | 接続詞を使わずに並べる                                                 |
| すでに定義した用語に付けるだけの枕詞（いわゆる、いわば）                                                   | 削って用語だけを書く                                                   |

## No Blame

書かれている事柄だけを扱い、人の動機や能力を疑う言い方を混ぜない。こうした言い方は、過去の失敗を受けて書く文書ほど入り込みやすい。

| 直す対象                                   | 直し方                         |
| ------------------------------------------ | ------------------------------ |
| 動機や能力を疑う言い方（口実に、抱え込む） | 起きた事柄と、必要な対応を書く |
| 個人を特定できる書き方（その人の不在中は） | 役割や仕組みの説明に直す       |
| 疑いを前提にした条件（利害のない）         | 満たすべき条件を直接書く       |

## One Topic per Paragraph

1つの段落では1つの話題だけを扱う。各段落の最初の文だけを読んでも流れがわかる順に並べ、前提から結論へ一方向に進める（議論を行き来させない）。

## One Point per Sentence

一文には1つのことだけを書く。読点やダッシュ（—）でつないで長くなった文は分け、文どうしの関係は接続詞か語順で示す。主語と述語を近づけ、間に挟まった修飾や条件、ダッシュによる補足は、前後の文か丸括弧に移す。ここまで直しても、修飾の掛かり先を二通りに読める文は残ることがある。その場合は、掛かり先が1つに決まるまで語順を変えるか、掛かる範囲を丸括弧で示す。読点は意味の区切りと掛かり先を示すためだけに打ち、間や強調のためには打たない。読点の位置でも掛かり先は変わるので、読点を動かして別の読み方ができないかも確かめる。

## Consistent Register

1つの文書の中で、敬体（です・ます）と常体（だ・である）を混ぜない。混ざっていれば、多いほうに揃える。新しく書くときは、書き加える先（同じリポジトリの既存のissue/PR、同じ文書群）で使われている文体に合わせる。見出しや箇条書き、表のセルでの体言止めや言い切りの形は、混在とみなさない。

## Headings

見出しは、節の内容をそのまま表す言い方にする。種別と主題のような2つの要素を詰め込まない。結論を言い切る決め台詞にしない。

## Spacing

日本語と半角英数字の間に半角スペースを入れない（「APIで取得」「v2へ移行」）。数字と助数詞の間も詰める（「1つ」「3件」）。ただし、次の2つは例外とする。書き加える先（既存の文書、リポジトリ）でスペースを空ける書き方が使われていれば、それに合わせる。issue/PR番号のすぐ後に日本語が続くときは、番号が自動でリンクになるようにスペースを入れる（「#12 を修正」）。

## Maintenance

表は型の一覧で、直した言葉の記録ではない。例や行が増え続けると表は単語の一覧になり、そこに挙がっている言葉や型しか見つけられなくなる。

見逃しを表に反映するときは、まず既存の行の型に当てはまるかを確かめ、当てはまるなら何も足さない（例は型ごとに1〜2個で足りる）。どの型にも当てはまらなければ、近い型と1つの行にまとめられないかを確かめ、まとめられないときだけ行を1つ足す。セルに収まるよう言葉を縮めて造語を作らない。セルの文言も本文と同じ基準で書く。

本文の説明は書き足さない。原則で説明できない見逃しがあったときに限り、原則の文を置き換える。表のない節（One Topic per Paragraph、One Point per Sentence、Headings、Spacing）も原則の文を置き換えるだけで対応し、例の表を新しく作らない。
